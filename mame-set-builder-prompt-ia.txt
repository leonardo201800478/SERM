PROMPT MESTRE — MAME SET BUILDER
Documento de contexto permanente para desenvolvimento assistido por IA

OBJETIVO
Este projeto é o MAME Set Builder, disponível em:
https://github.com/leonardo201800478/mame-set-builder

O objetivo final é transformar o projeto em uma ferramenta completa e especializada de gerenciamento e construção de sets MAME, combinando:
1. leitura e interpretação profunda do listxml.xml gerado pelo MAME;
2. classificação e filtragem eficiente de máquinas;
3. resolução correta das dependências entre máquinas, ROMs, BIOS, samples, discos/CHDs e dispositivos;
4. geração de DATs compatíveis com ferramentas de terceiros, como RomVault e outras ferramentas de gerenciamento de ROMs;
5. verificação do conteúdo existente no armazenamento local;
6. identificação precisa de arquivos faltantes;
7. integração com qBittorrent para utilizar um torrent/magnet de um full set MAME compatível e marcar somente os arquivos necessários para download;
8. posteriormente, reconstrução física de sets personalizados a partir de um full set existente;
9. futuramente, evolução para uma ferramenta completa de gerenciamento de ROMs MAME.

IMPORTANTE
A implementação deve ser gradual. Não reescrever todo o projeto de uma vez.
Antes de alterar código:
- examinar o estado atual do GitHub;
- identificar o que já existe;
- preservar componentes úteis;
- modificar uma camada por vez;
- executar testes após cada fase;
- evitar funcionalidades especulativas;
- documentar decisões arquiteturais;
- nunca assumir que uma informação precisa vir de arquivos externos se ela já estiver disponível no listxml.xml.

PRINCÍPIO ARQUITETURAL CENTRAL

Não confundir:
- estado de suporte do MAME;
- tipo/classificação da máquina;
- decisão do usuário sobre manter ou remover a máquina.

Uma máquina marcada pelo MAME como preliminary ou imperfect não deve ser automaticamente excluída.

Exemplo:
NAOMI, NAOMI 2, Sega Model 2 e Sega Model 3 podem possuir suporte imperfeito ou preliminar no MAME, mas continuam relevantes porque outros emuladores podem executá-los adequadamente.

- PRELIMINARY

- HANDHELD

- MECHANICAL
- DEVICE
- BIOS
- OTHER

User Policy:
- KEEP
- REMOVE
- AUTO

A política do usuário deve prevalecer sobre a avaliação de qualidade do driver quando configurada explicitamente.

ARQUIVOS INI

A arquitetura atual utiliza arquivos INI e classificações externas para determinadas decisões.

A meta é retirar os INIs do caminho principal quando a informação puder ser obtida diretamente do listxml.xml.

Os INIs poderão permanecer como fonte complementar/plugin caso seja comprovado que contêm uma informação realmente ausente do listxml ou necessária para uma classificação específica.

Não remover cegamente os INIs.
Primeiro mapear:
- quais dados eles fornecem;
- quais dados já existem no listxml;
- quais filtros dependem deles;
- quais podem ser substituídos;
- quais precisam continuar como fonte complementar.

DESEMPENHO

O código atual materializa muitas máquinas em objetos Python e aplica filtros em sequência.

Isso deve ser otimizado.

Prioridade:
1. parser XML eficiente;
2. processamento streaming quando possível;
3. armazenamento estruturado em SQLite;
4. índices adequados;
5. filtros executados no banco quando isso for mais eficiente;
6. evitar criar milhares de objetos Python desnecessariamente;
7. reduzir I/O;
8. cache inteligente;
9. multiprocessing/threading somente onde realmente trouxer ganho;
10. GPU somente quando existir uma operação realmente adequada para GPU.

Não utilizar GPU artificialmente.
Filtragem de XML, consultas SQLite e regras condicionais normalmente são tarefas de CPU/I/O e não justificam GPU.

CPU:
- explorar paralelismo em parsing, hashing ou processamento independente quando benchmarks comprovarem benefício;
- não usar multiprocessing apenas para aumentar uso de CPU;
- medir tempo antes/depois.

DEPENDENCY RESOLVER

Não assumir que uma máquina equivale simplesmente a name.zip.

Exemplo conceitual:

machine:
mk2

Pode depender de:
- ROM própria;
- parent;
- BIOS;
- arquivos compartilhados/merged;
- samples;
- discos/CHDs;
- outras dependências.

O Dependency Resolver deve transformar as máquinas selecionadas em um conjunto efetivo de arquivos necessários.

Resultado:
RequiredFiles

Cada RequiredFile deve possuir, quando aplicável:
- path;
- name;
- size;
- crc;
- sha1;
- machine;
- type;
- dependency source.

O resolver deve tratar corretamente:
- parent/clone;
- romof;
- bios;
- merge;
- samples;
- disk/CHD;
- optional;
- nodump;
- baddump;
- device dependencies;
- demais relações relevantes encontradas na documentação oficial.

DAT

O DAT deve ser consequência do SetManifest.

Fluxo:
seleção → dependências → SetManifest → DAT.

Não:
seleção → nomes de máquinas → DAT.

O DAT deve representar exatamente o conjunto selecionado e seus requisitos.

TORRENT / QBITTORRENT

Objetivo:
usar um magnet de um full set MAME correto e baixar somente os arquivos necessários.

Não é necessário reconstruir o torrent para isso.

Fluxo:
MAGNET
  ↓
adicionar ao qBittorrent
  ↓
aguardar metadata
  ↓
consultar lista de arquivos
  ↓
comparar com RequiredFiles
  ↓
marcar arquivos necessários
  ↓
desmarcar/não priorizar arquivos desnecessários
  ↓
iniciar/retomar torrent

O magnet não fornece necessariamente a árvore completa de arquivos imediatamente.
É necessário aguardar o qBittorrent obter os metadados.

Não assumir que o primeiro torrent retornado pela API é o torrent recém-adicionado.

O torrent deve ser identificado pelo hash/infohash retornado pela operação de adição ou por consulta robusta.

MATCHING DE ARQUIVOS

Não usar somente:
machine.name + ".zip"

Comparação preferencial:
1. caminho/nome normalizado;
2. tamanho;
3. CRC/SHA1 quando disponível;
4. regras de estrutura do torrent;
5. tratamento especial para CHDs/discos.

Resultado:
- MATCHED
- MISSING
- UNMATCHED
- AMBIGUOUS

Mostrar ao usuário quando o torrent parece ser de uma versão/set incompatível.

QBITTORRENT

Usar a Web API oficial/documentação atualizada.

Operações conceituais:
- adicionar magnet;
- identificar torrent;
- esperar metadata;
- obter conteúdo/arquivos;
- alterar prioridade individual;
- iniciar/pausar;
- consultar progresso.

Nunca presumir que endpoints ou comportamentos permanecem iguais sem verificar a documentação atual.

RECONSTRUÇÃO DE TORRENT

Não é a estratégia principal.

Criar um novo torrent contendo somente arquivos selecionados produziria outro infohash e não seria equivalente ao full set original.

Prioridade:
usar o torrent original e controlar prioridades.

PRINCÍPIO FINAL

O projeto não deve ser apenas um filtro de nomes de ROM.

Ele deve entender a estrutura do MAME.

A unidade principal não é "nome.zip".
A unidade principal é:

Machine → Dependencies → Required Files → SetManifest

E a partir desse manifesto devem ser derivados:
- DAT;
- verificação local;
- arquivos faltantes;
- seleção do torrent;
- download;
- rebuild.

Esse é o modelo arquitetural definitivo do MAME Set Builder.
