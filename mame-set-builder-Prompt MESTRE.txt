MAME SET BUILDER
ESPECIFICAÇÃO MESTRE DO PROJETO
Python + GUI
Versão conceitual: 1.0

======================================================================

1. OBJETIVO
   ======================================================================

Criar uma aplicação desktop para Windows, desenvolvida em Python, destinada
ao gerenciamento, filtragem, validação e construção de conjuntos
personalizados de ROMs para MAME.

O software NÃO deve distribuir ROMs, CHDs, BIOS ou qualquer conteúdo
protegido.

O software trabalha exclusivamente sobre arquivos que o usuário já possui.

O conceito central é:

FULLSET MAME
|
| leitura do listxml + configuração MAME + metadados
|
v
BANCO LOCAL
|
| filtros
v
MEU SET
|
| validação da fonte
| identificação por nome + CRC + SHA1
| dependências parent/clone/BIOS/device
v
CONSTRUÇÃO
|
v
DIRETÓRIO FINAL DO USUÁRIO

O FULLSET original deve ser considerado somente como FONTE.

O programa nunca deve modificar, mover, renomear ou apagar arquivos da
fonte durante a construção de um novo set.

A construção ocorre sempre:

SOURCE FULLSET -> DESTINATION MEU SET

Isso elimina a necessidade de backups internos do software e reduz o risco
de corrupção da fonte original.

======================================================================
2. PRINCÍPIOS FUNDAMENTAIS
==========================

2.1. MAME é a autoridade estrutural

O software deve utilizar o próprio MAME como fonte primária das informações.

A principal fonte de dados é:

```
mame.exe -listxml
```

O XML contém informações estruturais extremamente importantes, incluindo:

* nome da máquina
* descrição
* fabricante
* ano
* sourcefile
* cloneof
* romof
* sampleof
* BIOS
* devices
* ROMs
* tamanho
* CRC
* SHA1
* merge
* region
* offset
* status
* optional
* chips
* displays
* input
* controls
* driver
* estado de emulação
* features
* software lists
* slots
* RAM
* etc.

O programa não deve tentar recriar essas informações manualmente quando
elas podem ser obtidas diretamente do MAME.

2.2. Versão do MAME

A versão do MAME deve ser descoberta automaticamente a partir do executável
selecionado pelo usuário.

Nunca assumir:

```
MAME 0.xxx
```

O banco de dados deve possuir:

```
mame_version
executable_path
executable_hash
listxml_generation_date
```

O banco deve permitir coexistência de bancos provenientes de diferentes
versões do MAME.

2.3. Fullset como fonte imutável

Exemplo:

```
D:\MAME_FULLSET\
```

será tratado como fonte.

O resultado pode ser:

```
E:\MEU_MAME\
```

O programa copia somente os arquivos necessários.

Nunca modificar:

```
D:\MAME_FULLSET\
```

======================================================================
3. FORMATOS DE SET
==================

O programa deve suportar:

NON-MERGED
SPLIT
MERGED

NON-MERGED

Cada máquina possui seu conjunto completo de ROMs necessárias.

Exemplo conceitual:

```
sf2.zip
sf2ce.zip
sf2hf.zip
```

SPLIT

ROMs comuns ficam no parent e clones carregam somente diferenças.

Exemplo:

```
sf2.zip
sf2ce.zip
sf2hf.zip
```

MERGED

Parent e clones são armazenados juntos em um único arquivo.

Exemplo:

```
sf2.zip
```

contendo ROMs do parent e clones.

REGRAS DE INTERFACE

Se o usuário escolher MERGED:

```
"Remover clones" deve ficar desabilitado.
```

Tooltip:

```
"Sets MERGED armazenam parent e clones no mesmo arquivo. A remoção
 individual de clones não é aplicável durante a construção física
 do arquivo."
```

Se NON-MERGED ou SPLIT:

```
"Remover clones" pode ser habilitado.
```

23. IDENTIFICAÇÃO DE ROM
========================

NÃO considerar apenas:

```
nome_do_zip.zip
```

O ZIP/7Z deve ser aberto e seus arquivos internos analisados.

Exemplo:

```
mk.zip
```

pode conter:

```
sl1_mortal_kombat_u3_sound_rom.u3
...
l5_mortal_kombat_t-unit_uj12_game_rom.uj12
```

Cada entrada deve ser identificada por:

```
filename
size
CRC32
SHA1
```

A correspondência ideal será:

```
machine
   |
   +-- rom
         |
         +-- filename
         +-- crc
         +-- sha1
         +-- size
```

O nome do arquivo é um identificador auxiliar.

CRC e SHA1 são identificadores fundamentais.

======================================================================
24. SCANNER DE ARQUIVOS
=======================

Scanner deve trabalhar em paralelo.

CPU:

```
multiprocessing
ProcessPoolExecutor
```

ou arquitetura equivalente.

Não utilizar threads Python para tarefas intensivas de hashing como
estratégia principal quando o GIL representar gargalo.

Threads podem ser utilizadas para I/O.

Processos devem ser utilizados para CPU-bound.

AVX2:

O software deve detectar recursos de CPU.

Se houver implementação nativa/externa de hashing que aproveite AVX2,
poderá ser utilizada.

Não criar código AVX2 em Python puro apenas para dizer que usa AVX2.

GPU:

Não utilizar GPU para operações que sejam mais lentas ou complexas que CPU.

A primeira prioridade é:

```
SSD
leitura sequencial
multiprocessing
cache
banco indexado
hashing somente quando necessário
```

======================================================================
33. TORRENT
===========

O sistema NÃO deve assumir que um magnet link consegue simplesmente
"selecionar ROMs".

Magnet link identifica um torrent através de metadados.

A seleção granular depende da estrutura do torrent e da capacidade do
cliente.

O projeto deve separar:

```
Torrent Discovery
Torrent Metadata
Torrent File Tree
Missing Matcher
qBittorrent Integration
```

Fluxo:

```
FULLSET esperado
      |
      v
MISSING ROMS
      |
      v
TORRENT
      |
      v
comparar árvore do torrent
      |
      v
identificar arquivos correspondentes
      |
      v
gerar seleção de download
```

A aplicação deve preferir trabalhar com:

```
.torrent
```

quando disponível.

Depois:

```
magnet + metadata obtida pelo cliente.
```

O programa NÃO deve tentar modificar um torrent existente.

Recriar um torrent é uma operação futura e separada.

======================================================================
34. QBITTORRENT
===============

A integração com qBittorrent deve ser feita por Web API.

O software deve:

1. conectar
2. adicionar torrent/magnet
3. obter metadata
4. listar arquivos
5. comparar nomes/tamanhos
6. identificar índices dos arquivos necessários
7. marcar arquivos selecionados
8. iniciar download

A seleção deve ocorrer por índice de arquivo do torrent.

Nunca assumir que:

```
nome da ROM == nome do arquivo torrent
```

Normalizar caminhos antes de comparar.
